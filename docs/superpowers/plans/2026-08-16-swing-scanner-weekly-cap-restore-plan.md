# Swing Scanner Weekly-Cap Restoration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a one-time-per-week Telegram notice to the Swing Scanner's existing weekly send-cap gate, so hitting the cap is visible instead of a silent skip, then deploy the updated scanner live.

**Architecture:** `src/swing-scanner.src.js` in this worktree (branched from `main` HEAD) already contains the `MAX_WEEKLY_SENDS = 15` constant and its gate (`if (thisWeekCount >= MAX_WEEKLY_SENDS) { ...; return [{ json: { skipped: true, ... } }]; }`) — this was never removed by any commit. The gate itself does not need restoring in this branch. What it lacks is any user-visible signal when it trips: it returns silently, which is exactly what produced the 2026-08-12 "왜 스캔 알림이 없냐" confusion ([[swing-algo-weekly-cap-silent-skip-2026-08-12]]). This plan adds a one-time Telegram notice the first time the cap trips each week, without spamming on every subsequent 10-minute cycle that week.

Separately (out of scope for this plan's code changes, noted for deploy-time awareness): the **live** deployed Swing Scanner node currently has this gate entirely removed, and the **main checkout** (outside this worktree, at `D:\vibecording\showmoneyv2\src\swing-scanner.src.js` / `swing_scanner_code.js`) has an uncommitted, unreviewed local edit that matches — a clean 8-line removal of just the constant and gate block, nothing else. The user has been informed and this plan's Task 4 deploy will overwrite that live state with the version built from this branch (which has the gate restored, matching pre-removal behavior, plus this plan's new notice).

**Trader-perspective note:** the underlying volume-cap value (15/week) is not changed here — no new evidence from this week's data argues for a different number, and the earlier brainstorm already established that tightening score/grade thresholds is not well-supported by this week's live data (score means overlap heavily between win and loss groups, consistent with [[swing-algo-sub-project-5b-hitrate90-hold5]]'s and [[swing-algo-sub-project-10-signal-weight-refit]]'s prior near-chance findings). This plan is deliberately narrow: restore the visibility the cap needs to stay in production without getting quietly stripped out again.

**Tech Stack:** n8n Function-node script (plain JS, no npm deps), existing `lib/telegramClient.js` (`telegram.send`), existing self-check convention (`scripts/verify_*.js`, plain `assert`-style, no test framework), the n8n Cloud REST API deploy mechanism already used for the sibling Daily-Position-Monitor plan (`PUT https://fastlane12.app.n8n.cloud/api/v1/workflows/ScHaeFdneOoH1ZNZ`, API key read at runtime from `export_n8n_executions.py` in the main checkout — never hardcoded in committed scripts).

### Task 2: Regression self-check for the notice logic

**Files:**
- Create: `scripts/verify_swing_scanner_weekly_cap.js`

**Interfaces:**
- Consumes: nothing from Task 1 (mirrors the logic by duplication — `src/swing-scanner.src.js` has a top-level `return run();` and is not requireable by plain Node, same constraint as the other n8n Function-node scripts in this repo).
- Produces: nothing consumed elsewhere; standalone `node scripts/verify_swing_scanner_weekly_cap.js` check.

- [ ] **Step 1: Write the self-check script**

```javascript
/**
 * Self-check for the one-time weekly-cap-reached notice added to
 * src/swing-scanner.src.js (shouldSendWeeklyCapNotice gate).
 * Mirrors the exact decision logic so a future edit that breaks the
 * once-per-week notice behavior fails this script.
 *
 * Run: node scripts/verify_swing_scanner_weekly_cap.js
 */
'use strict';

function shouldSendWeeklyCapNotice(thisWeekKey, lastNotifiedWeek) {
  return lastNotifiedWeek !== thisWeekKey;
}

function main() {
  let failures = 0;
  const assertEq = (label, got, want) => {
    if (got !== want) { failures++; console.error(`FAIL ${label}: got ${got}, want ${want}`); }
  };

  // Case 1: never notified before (undefined) -> send notice
  {
    const result = shouldSendWeeklyCapNotice('2026-08-10', undefined);
    assertEq('never notified before sends notice', result, true);
  }

  // Case 2: cap trips again later the same week (same week key) -> do not re-send
  {
    const result = shouldSendWeeklyCapNotice('2026-08-10', '2026-08-10');
    assertEq('same week already notified does not resend', result, false);
  }

  // Case 3: a new week starts (different week key) -> send notice again
  {
    const result = shouldSendWeeklyCapNotice('2026-08-17', '2026-08-10');
    assertEq('new week sends notice again', result, true);
  }

  // Case 4: repeated calls within the same tripped week stay suppressed
  {
    const first = shouldSendWeeklyCapNotice('2026-08-10', undefined);
    assertEq('first call in week sends', first, true);
    // production code sets store.swingWeeklyCapNotifiedWeek = '2026-08-10' after Case 4's first call
    const second = shouldSendWeeklyCapNotice('2026-08-10', '2026-08-10');
    assertEq('second call same week suppressed', second, false);
    const third = shouldSendWeeklyCapNotice('2026-08-10', '2026-08-10');
    assertEq('third call same week still suppressed', third, false);
  }

  if (failures > 0) {
    console.error(`${failures} case(s) failed`);
    process.exit(1);
  }
  console.log('OK: weekly-cap one-time-notice logic verified (4 cases).');
}

main();
```
