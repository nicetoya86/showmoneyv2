Backtest Report swing-scanner.src.js — Profitability Review ● Marginal edge, concentrated in top score tier & highly sensitive to entry-fill timing

A modest, real edge — carried almost entirely by 110+ scored trades

Faithful Python port of the production swing-recommendation engine, backtested across 200 KRX tickers from 2024-01-01 to 2026-01-01. 1,202 trades generated, sorted by pattern, score tier, and a reconstruction of a regime-blocking rule that has silently rotted into dead code. The headline edge below is highly sensitive to the backtest's entry-fill assumption — entries are booked at the signal day's close rather than a realistically fillable next-day price, and most of the reported edge is overnight gap, not selection skill (see the Entry-Fill Sensitivity panel below).

Entries in this backtest are booked at the signal day's close (entry=current_price), not next-day open — a prior version of this report incorrectly claimed the latter. The exit walk starts the next trading day, but PnL is still computed against the stale signal-day close, so every trade silently books the full overnight gap (average +0.786%/trade) as free profit — essentially the entire headline edge. Re-pricing entry at the actual next-day open across all 1,202 trades collapses avg PnL from +0.886% to +0.142% and win rate from 40.68% to 39.68%. This is also why Finding 5 (Toss TOSS-LIVEPRICE) below is reframed as an upper bound, not a lower bound, on realized PnL.

Code Review Findings

from docs/03-analysis/swing-algorithm-profitability-review.analysis.md
1
Regime-blocking gate silently regressed to dead code
getMarketRegime() computes a KOSPI/KOSDAQ + macro regime level, but the entry-blocking check that once used it is gone from the current file — production has been trading regime-blind while logs still imply the safety layer is active. Measured impact this run: marginal (see Regime Gate panel above).
Fix regardless of measured impact
2
Two indicator implementations are dead code
calcBB() (Bollinger Bands) and detectCupAndHandle() are fully implemented but never called from candidate generation — maintenance surface with zero effect on trading decisions.
Remove or wire up
3
Scoring weights never statistically validated
The ~15 bonuses/penalties above were set from a 30-stock hindsight review, not fit or cross-validated against a larger dataset. This backtest is the first genuine out-of-sample check they've received.
Re-tune from this backtest
4
Pipeline is fragile under upstream data-format changes
A Naver API normalization regression (missing BOM/Buffer/string-JSON handling) silently zeroed 15 real recommendations in the weekly report this session. The same catch(e) { return null } pattern appears throughout the candidate-generation path.
Audit remaining call sites
5
Toss confirmation is unmeasured — and its omission inflates PnL, not just trade count
tossConfirm() blocks unfavorable-orderbook sends live with no historical equivalent — on its own this only reduces trade count, so the backtest stays an upper bound on trade frequency. But TOSS-LIVEPRICE (added 2026-07-19) also rebases entry/target/stop onto the live price and blocks sends that already reached target/stop by the 09:10 send time — exactly the overnight-gap profit this backtest books (see Entry-Fill Sensitivity above). So this backtest is an upper bound on realized PnL relative to production, not a lower bound as previously stated.
PnL direction corrected — upper bound, not lower
Read this backtest with these caveats in mind:
  • No transaction costs are modeled anywhere — no brokerage fees, 증권거래세 (securities transaction tax), or slippage. A realistic KRX round trip runs roughly 0.15–0.2% (sell-side tax plus commission both ways). Against the +0.886% signal-day-close headline this is a meaningful haircut; against the +0.142% next-day-open sensitivity figure above, it plausibly flips the sign to net-negative.
  • Every simulated trade is held one day longer than production intends — backtest/simulate_exits.py's exit loop runs hold_days + 1 bars, not hold_days, because production's "최대 N거래일" counts the entry day itself. This gives every trade one extra chance to touch target/stop before timing out. Not an implementer bug — a plan-pinned fidelity detail, disclosed here.
  • KRX supply data was unavailable all run — the foreign/institutional net-buy endpoint returned HTTP 400 for every call in this environment (a known session/auth limitation, handled gracefully, not a crash). Every trade above was generated primarily from price/volume signals; supply-based bonuses and the negative-supply hard-block never fired, and DART disclosures contributed to only a small minority of trades (only ~18 of 1,202 had any same-day disclosure, only ~2 matched a positive keyword) — expected given production's page_count=100 pagination limit, not a bug.
  • Regime what-if reconstruction is directionally, not exactly, faithful — besides the gap-detection simplification noted in Finding 1's panel above, the macro overlay compares a Korean trading day to the same-calendar-date NASDAQ/VIX close (the US session actually closes ~06:00 KST the next day), and SP500_DOWN_THRESH — one of production's three macro triggers — is commented out/unused in the reconstruction. Affects only the secondary what-if comparison, whose "marginal effect" conclusion is robust to this.
  • Drawdown/equity figures are illustrative, not a portfolio simulation — they compound all 1,202 trades sequentially in one account rather than modeling the up-to-3-concurrent-positions/day the algorithm actually allows. Treat win rate / avg PnL / median PnL as the primary signal of edge; treat −92.80% MDD and 1855.16× equity as an artifact of that simplification, not a real portfolio outcome.
